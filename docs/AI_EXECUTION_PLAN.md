## 1. 结论：不转 C++/Qt

当前应用的核心性能问题在浏览器端的数据流和状态更新，不在 JavaScript 语言本身。C++/Qt 可能提高本地绘制速度，但会带来：

- Windows/macOS/Android/iOS 多端打包与签名。
- 安装、升级、崩溃排查和商店审核成本。
- 与 Cloudflare Pages / D1 的接入重写。
- 现有 Web 获客能力丢失。
- 继续维护 Web + Qt 两套客户端。

只有当出现"系统级划词、托盘常驻、超大本地词库、严格帧率/内存控制"等明确桌面需求时，才考虑 Qt 作为独立增强客户端。当前主线仍使用：

- 前端：现有 HTML/CSS/JavaScript，逐步迁移 TypeScript 模块。
- 服务端：Cloudflare Pages Functions / Worker。
- 数据：D1 + JSON 内容分片。
- 缓存：Service Worker + 浏览器存储。

## 2. 性能目标

### 2.1 P0 用户可感知指标

| 指标 | 目标 | 测量方式 |
|---|---:|---|
| 冷启动首卡片 | < 800 ms | Edge/Chrome 全新 profile，生产构建 |
| 热启动首卡片 | < 300 ms | 已缓存 shell 和词库 |
| 首次打开 DOM | < 400 节点 | Performance/DOM count |
| 首屏 HTML gzip | < 20 KB | 构建产物 |
| 首屏关键 JS gzip | < 45 KB | 构建产物 |
| 滑动交互 | 无明显掉帧 | 100 次/1000 次滑动 p50/p95 |
| 章节切换 | < 300 ms 显示可用卡片 | 当前牌组、当前章节 |
| 详情打开 | < 200 ms 本地命中 | 相应字母分片已缓存 |
| localStorage 同步写入 | 不进入 pointermove 热路径 | 写入计数/耗时 |
| 静态请求 D1 查询 | 0 次 | Worker 路径检查 |

### 2.2 测量前置

必须使用：

- 生产模式构建，不能使用开发模式结论。
- 全新 `--user-data-dir` 的 Edge/Chrome，不能依赖旧 Service Worker。
- 分别在冷缓存、热缓存、离线三种状态测量。
- 至少记录 p50、p95，而不是只报最快一次。
- 移动端模拟 CPU 降速 4x 或使用真实 Android 设备。

### 2.3 必测场景

1. 首次访问，无缓存，联网。
2. 关闭浏览器后热启动。
3. 离线启动。
4. 第一章 200 词加载。
5. 从上次第 80 个词恢复。
6. 打乱后重启。
7. 详情分片首次加载与后续命中。
8. 音频在线、缓存命中、系统语音回退。
9. 登录、退出、切换账号后的进度恢复。
10. 双设备同步冲突合并。

## 3. 优化优先级

### P0：先修真实瓶颈

1. **主线程堵塞**
   - 排查大对象 `JSON.stringify`。
   - 排查滑动/点击时的多次全量渲染。
   - 排查 localStorage 同步写入。
   - 排查长任务（Long Task > 50 ms）。

2. **启动路径**
   - 确认首屏只解析必要数据。
   - 确认不提前构建全词表和全位置索引。
   - 确认章节补全不会重复请求同一分片。
   - 确认恢复位置不会先渲染错误的第一张卡。

3. **章节与详情**
   - 当前章节优先。
   - 详情按字母分片。
   - 请求去重、失败重试有界。
   - 对同一资源避免瀑布式串行请求。

4. **缓存一致性**
   - shell、数据、音频和 Service Worker 版本对齐。
   - 页面标记和实际缓存一致。
   - SW 更新不导致错误词或旧页面。

5. **同步与账号**
   - 进度写入合并、批量 flush。
   - 同步请求不阻塞滑动。
   - 合并只保留一个实现。
   - 云端恢复使用同一个 resume 用例。

### P1：减少不必要工作量

6. 列表虚拟分页或增量渲染。
7. 音频预取：只预取当前和后续少量词。
8. 低优先级任务使用 `requestIdleCallback` 或合适的分批调度。
9. 避免重复序列化、重复索引、重复排序。
10. 移除未使用资源和旧分片。

### P2：结构性优化

11. localStorage 大对象迁移到 IndexedDB。
12. 把 `template.html` 按 storage、API、deck、study、sync、audio、view 拆模块。
13. 建立 TypeScript 契约和单元测试。
14. 构建内容哈希、manifest 和可复现构建。
15. 建立 CI 性能门禁。

## 4. 具体优化方案

### 4.1 localStorage 热路径治理

问题：

- localStorage API 是同步的。
- 每次滑动都序列化整份学习状态，可能造成移动端卡顿。
- 音标、详情、设置等数据与学习状态混在一起会放大写入量。

目标：

- pointermove 不写存储。
- pointerup 只提交一个轻量状态变更。
- 高频状态按批次持久化。
- 页面隐藏时 flush。
- 大对象迁移到 IndexedDB。

步骤：

1. 在现有 `save` 附近增加调试计数器，记录 key、字节数、调用次数（仅测试环境）。
2. 找到滑动、导航、拖拽、撤销的调用链。
3. 确保 pointermove 不调用存储。
4. 将状态写入合并为 100–300 ms 的批次，关键动作立即 flush。
5. 把大学习记录迁移到 IndexedDB；小配置和登录标记保留 localStorage。
6. 首次迁移时支持双读，迁移成功后写入版本标记。
7. 失败时回退到 localStorage，不能丢进度。

验收：

- 100 次滑动中，localStorage 写入次数显著下降且没有按 pointermove 触发。
- 刷新和浏览器重启后进度一致。
- 离线、账号切换、导入导出测试全绿。

### 4.2 IndexedDB 迁移设计

建议存储：

- `progress`：按账号作用域的单词状态。
- `chapters`：章节顺序和位置快照。
- `daily`：每日统计。
- `meta`：schema 版本、迁移状态、最后更新时间。

不要把所有数据放进一个无限增长的 value。按账号和词条分片，使用批量事务。

迁移规则：

1. 读取旧 localStorage。
2. 以版本号执行一次性迁移。
3. 校验记录数和关键字段。
4. 写入 IndexedDB 成功后再删旧 key。
5. 任何失败保留旧数据。
6. 提供回滚逻辑。

验收：

- 大状态写入不阻塞交互。
- 10k 词进度模拟测试可完成任务。
- 进度、章节、每日统计、账号隔离全部正确。

### 4.3 滑动与渲染优化

要求：

- `pointermove` 只更新 transform / opacity 等局部样式。
- `pointerup` 只执行一次状态命令。
- 不重建所有 DOM。
- 不在每一次渲染中重新计算完整队列。
- 不重复设置相同文本、class、属性。

检查项：

- 是否存在 50 ms 以上长任务。
- 是否存在每次滑动都 `JSON.stringify(state)`。
- 是否存在同步音频、同步统计、同步同步请求。
- 是否存在多个事件监听器重复触发。

AI 修改规则：

- 一次只改一个热路径。
- 先加性能打点，再改逻辑。
- 保留现有手势判定和边界行为。
- 完成后对比 p50/p95 和 DOM 变化。

### 4.4 启动与章节恢复优化

已确认语义：

- 启动 HTML 最多内联 40 条词数据，不是显示 40 个词。
- 第一章应显示 200 个词。
- 上次学习位置必须恢复。
- 上次目标词不在前 40 条时，不得先显示并保存第一个词。

当前必须保持：

- `savePos()`
- `resumePosition()`
- `deckChapter`
- `posWord`
- `pendingSeek`
- `chapterExpectedLength`
- `fillDeckInBackground`

目标：

- 启动先读取作用域和 resume 元数据。
- 数据不足时进入恢复加载态。
- 补全完成后按 `posWord` 定位。
- 找不到 `posWord` 才按保存的 `pos` 夹取。
- 最后才回落章节起点。

禁止：

- 另写第二套章节补全。
- 用 `loadChapter(0)` 无条件覆盖保存位置。
- 先显示第一词再跳到上次词。

### 4.5 详情分片优化

目标：

- 只加载当前首字母详情。
- 同一字母请求去重。
- 缓存命中不重新请求。
- 失败分片不缓存空结果。
- 切换单词时取消无效请求。
- 详情加载不阻塞卡片切换。

验收：

- 首次详情打开 < 200 ms 本地命中。
- 同一字母第二次打开不产生网络请求。
- 断网时有合理回退。
- 失败后重试可以恢复。

### 4.6 音频优化

顺序：

1. 当前词音频预取。
2. 后续少量词预取。
3. 优先缓存命中。
4. 在线失败回退系统语音。
5. 不在用户滑动时同步等待音频。

禁止：

- 每个词都并发请求。
- 无上限扩张缓存。
- 把未成功写入缓存标记为已缓存。
- 旧词音频淘汰后仍显示"已缓存"。

验收：

- 热缓存播放 p95 < 100 ms。
- 在线异常可回退。
- 离线命中正常。
- 缓存预算和淘汰策略可观测。

### 4.7 Service Worker 与缓存

要求：

- HTML/SW 不缓存旧版本。
- 数据文件使用内容哈希和 immutable cache。
- shell、数据、音频版本一致。
- SW 更新有提示或明确的激活策略。
- 不使用旧缓存结果判断上线。

验收：

- fresh profile 可加载最新版。
- 旧 SW 不返回不一致页面。
- 离线重启可用。
- 数据分片命中率和体积符合预算。

### 4.8 同步与 Worker

要求：

- 静态请求不访问 D1。
- 同步写合并为一个轻量请求。
- 限制 body 大小并防止 gzip bomb。
- 错误码稳定，不泄露 SQL。
- 合并逻辑唯一。
- 账号和游客作用域隔离。

验收：

- 1000 次模拟同步无重复写。
- 冲突返回可解释。
- 请求失败不阻塞前台滑动。
- Worker route 和 repository 可单独测试。

## 7. 每次改动必须保护的现有能力

- 首屏一次性只内联最多 40 条词数据。
- 第一章仍按 200 词加载。
- 首次有效进度恢复不闪回第一词。
- 关闭浏览器再打开回到上次词。
- 离线可启动。
- 音频缓存和页面标记一致。
- 账号作用域隔离。
- 进度导入导出正确。
- 合并逻辑唯一。
- 静态资源不经过 D1。
- 旧 Service Worker 不污染上线验证。

## 8. 什么时候才考虑原生客户端

只有同时满足以下条件才考虑 Qt/C++ 桌面客户端：

1. 明确存在桌面端专属需求。
2. Web 端性能测量确认无法通过算法、存储或缓存优化解决。
3. 有独立客户端团队和维护预算。
4. 后端 API、D1 和数据库契约已经稳定。
5. 能接受 Web 与桌面两端并行维护。

推荐形态：

```text
现有 PWA
  + 可选 Qt 桌面客户端
  + 共用现有 Worker API / D1
  + Qt 本地 SQLite 缓存
```

不推荐把整个 Web 项目重写成 Qt。
